quota 테스트가 쓰는 클럭이 파일 전역에 남아 댕글링 포인터가 되고, 이후 실행되는 다른 테스트를 크래시시키는 문제를 고쳤습니다. 다른 CL을 검증하다 우연히 만난 크래시였고, **버그 리포트도 이슈도 없던 것**을 재현·원인 규명까지 해서 CL로 만든 첫 사례입니다.

## 문제 설명

- issue url: 없음 (crbug 미등록. 직접 발견)
- `QuotaDatabase`의 테스트용 클럭은 `.cc` 파일 전역입니다.

  ```cpp
  const base::Clock* g_clock_for_testing = nullptr;
  // ...
  return g_clock_for_testing ? g_clock_for_testing->Now() : base::Time::Now();
  ```

- `SetClockForTesting()`은 이 전역을 덮어쓰기만 하고, **되돌리는 책임은 호출자에게** 있었습니다.
- `QuotaDatabaseTest`는 생성자에서 `SimpleTestClock`을 심어놓고 되돌리지 않습니다. 픽스처가 소멸하면 클럭 객체는 해제되는데 전역 포인터는 그대로 남습니다. 같은 프로세스에서 이후에 실행되는 테스트가 `GetNow()`에 닿는 순간 **해제된 객체에 가상 호출**을 하게 됩니다.

  ```
  Received signal 11 SEGV_MAPERR 000000000010
  #4  storage::QuotaDatabase::QuotaDatabase()
  #5  storage::QuotaManagerImpl::EnsureDatabaseOpened()
  #6  storage::QuotaManagerImpl::UpdateOrCreateBucket()
  #7  storage::QuotaManagerImplTest::RegisterClientBucketData()
  #8  QuotaManagerImplParamTest_ReportedQuotaConfigurability_Test::TestBody()
  ```

- 이 크래시는 quota 테스트를 한 배치로 돌릴 때만 납니다. `QuotaDatabaseTest`가 먼저 실행돼야 하기 때문입니다. 해당 테스트만 단독으로 돌리면 통과하므로, 겉보기엔 **수명 버그가 아니라 flaky처럼** 보입니다.

## 해결 내용

`SetClockForTesting()`이 `base::AutoReset`을 반환하도록 바꿔서, 반환값이 스코프를 벗어나면 클럭이 자동으로 복구되게 했습니다.

```diff
-  static void SetClockForTesting(const base::Clock* clock);
+  // Overrides the clock returned by GetNow() until the returned object goes
+  // out of scope, which restores the previous clock.
+  static base::AutoReset<const base::Clock*> SetClockForTesting(
+      const base::Clock* clock);
```

픽스처는 이 반환값을 멤버로 보관합니다. **선언 순서 덕분에 소멸 순서가 저절로 맞습니다** — `clock_override_`가 `clock_`보다 뒤에 선언되어 있으므로 먼저 소멸하면서 전역을 복구하고, 그 다음에 클럭 객체가 해제됩니다.

```cpp
  QuotaDatabaseTest()
      : clock_(std::make_unique<base::SimpleTestClock>()),
        clock_override_(QuotaDatabase::SetClockForTesting(clock_.get())) {}
  // ...
  std::unique_ptr<base::SimpleTestClock> clock_;
  base::AutoReset<const base::Clock*> clock_override_;
```

### 왜 한 줄로 끝내지 않았나

`TearDown()`에 `SetClockForTesting(nullptr)` 한 줄만 넣어도 이 크래시는 사라집니다(실제로 확인했습니다). 그런데 `quota_manager_unittest.cc`에 같은 set/reset 쌍이 **7개 더** 있고, **7쌍 모두 사이에 `ASSERT_*`가 있습니다.**

```cpp
  QuotaDatabase::SetClockForTesting(clock.get());
  // ...
  ASSERT_FALSE(UpdateOrCreateBucket(params).has_value());   // 실패하면 여기서 return
  // ...
  QuotaDatabase::SetClockForTesting(nullptr);               // 건너뜀
```

단언이 하나 실패하면 되돌리기를 건너뛰고, **테스트 실패 하나가 엉뚱한 곳의 크래시로 번집니다.** 방금 제가 한 시간 넘게 쫓은 것이 정확히 그 현상이었습니다. 그래서 호출자를 고치는 대신 API가 스스로 되돌리게 했습니다. `base::AutoReset`은 클래스 자체가 `[[nodiscard]]`라 반환값을 받지 않으면 컴파일러가 경고합니다.

### 설계 판단의 근거

혼자 정하기보다 트리에서 관행을 조사했습니다.

| 확인한 것 | 결과 |
|---|---|
| 스타일 가이드 | `ForTesting`은 **명명과 테스트 전용 제한**만 규정. RAII 여부는 규정 없음 |
| 관행 분포 | `void SetXForTesting` 558개 대 `AutoReset` 반환 51개 — **다수파는 여전히 void** |
| 추세 | AutoReset 반환 표본이 전부 2025년(1월·9월·11월) — 최근 늘고 있음 |
| 직접 선례 | `chromeos_reimpl_navigation_capturing_throttle.h`에 **클럭에 대한 같은 형태**가 이미 있음 |
| 프로젝트 방침 | `docs/testing/identifying_tests_that_depend_on_order.md`: *"stamp out all the tests that have ordering dependencies"* |
| 파급 범위 | 호출처가 전부 quota 안의 테스트 → 프로덕션 위험 없음 |

다수파가 void라는 점은 이 제안의 약점입니다. 리뷰어가 최소 수정을 원하면 픽스처 소멸자 한 줄로 물러설 수 있고, 그건 리뷰에서 정할 문제라고 보고 근거를 갖춘 쪽을 먼저 냈습니다.

## 발굴 과정 — 그리고 제가 한 실수

quota의 만료된 `NotFatalUntil` 정리 CL을 검증하는데 `storage_unittests`가 SIGSEGV로 죽었습니다. 처음엔 제 변경 탓이라고 결론 내렸는데 **틀렸습니다.**

- 실패한 실행은 러너 필터로 **321개** 테스트를 돌렸고
- 제가 origin/main과 비교할 때 쓴 필터는 **8개**짜리였습니다

조건이 달랐습니다. 8개로는 main이 통과하니 "내가 깨뜨렸다"로 보였지만, **같은 321개 필터로 main을 돌리자 똑같이 크래시**했습니다. 사전 실패였습니다.

그 사이 이분 탐색을 다섯 번 돌렸고 결과가 서로 모순됐습니다 — "9번까지 적용하면 통과, 10번을 더하면 실패"인데 "10번만 적용하면 통과". **그 모순 자체가 재현 조건이 흔들린다는 신호**였는데 늦게 알아챘습니다.

## 테스트 방법

`storage_unittests`의 quota 관련 테스트 321개를 한 배치로 돌려 비교했습니다.

| | 결과 |
|---|---|
| origin/main | `ReportedQuotaConfigurability`에서 **SIGSEGV**, 이후 6개 미실행 |
| main + `TearDown` 한 줄 | **321/321 통과** (원인 확정) |
| 최종 AutoReset 판 | **321/321 통과** |

## 배운 점

- **대조군은 조건을 한 글자도 바꾸지 않고 잡아야 합니다.** 필터가 다른 두 실행을 비교하면 엉뚱한 결론이 나옵니다. 실패를 만나면 가장 먼저 base로 되돌려 **똑같은 명령**으로 재현하고, 결과가 같으면 사전 실패로 처리하는 게 순서입니다.
- **이분 탐색은 재현이 결정적임을 확인한 뒤에 시작합니다.** 결과가 서로 모순되면 탐색을 멈추고 조건부터 고정해야 하는데, 저는 모순을 보고도 탐색을 계속했습니다.
- **버그의 원인이 호출자가 아니라 API인 경우가 있습니다.** 되돌리기를 잊게 만드는 설계라면 호출자를 하나씩 고치는 것은 증상 치료입니다. 타입으로 강제할 수 있으면 그쪽이 낫습니다.
- **트리는 스타일 가이드보다 많은 것을 알려줍니다.** 문서에 규정이 없어도 관행 분포와 최근 추세, 유사 선례를 세어보면 제안의 근거가 됩니다.
