`//storage/browser/quota`의 CHECK 153곳에 남아 있던 만료된 `base::NotFatalUntil::M148` 인자를 제거했습니다. 헤더가 직접 지시하는 뒷정리이고, **제가 앞서 머지한 CL이 같은 근거로 이미 일부를 제거한 in-tree 선례**가 있어 근거가 명확한 작업이었습니다.

## 문제 설명

- issue url: 없음 (crbug 미등록. 원 CL도 `Bug:` 트레일러가 없는 순수 정리 CL이었습니다)
- Chromium에는 새 `CHECK`를 단계적으로 켜는 장치가 있습니다. `CHECK(cond, base::NotFatalUntil::M148)`은 M148 전까지 프로세스를 죽이지 않고 덤프만 남기고, 그동안 크래시 리포트를 모아 "켜도 되는지"를 확인하라는 뜻입니다.
- 판정은 `base/check.cc`가 합니다. **지정 마일스톤이 현재 마일스톤 이하이면 그냥 `LOGGING_FATAL`** 입니다.

  ```cpp
  LogSeverity GetNotFatalUntilSeverity(base::NotFatalUntil fatal_milestone) {
    if (... std::to_underlying(fatal_milestone) <= BASE_CHECK_VERSION_INTERNAL) {
      return LOGGING_FATAL;
    }
    return GetDumpSeverity();
  }
  ```

  현재 `chrome/VERSION`의 MAJOR는 155이므로 148 ≤ 155, 즉 이 CHECK들은 **이미 7개 마일스톤째 fatal**이고 인자는 아무 효과 없이 남아 있었습니다.
- 정리 방법은 헤더 자신이 지시합니다.

  > [base/not_fatal_until.h] To clean up old entries remove the already-fatal argument from CHECKs as well as from this list. This generates better-optimized CHECKs in official builds.

- 원 커밋은 2026-02-26의 [CL 7601393](https://crrev.com/c/7601393) "Quota: change DCHECK to CHECK in //storage/browser/quota"입니다.

## 해결 내용

10개 파일에서 153곳의 인자를 제거했습니다. 조건과 `<<` 스트림 메시지는 그대로 두었습니다.

```diff
 void QuotaTask::Start() {
-  CHECK(observer_ != nullptr, base::NotFatalUntil::M148);
+  CHECK(observer_ != nullptr);
   observer()->RegisterTask(this);
```

| 파일 | 곳수 |
|---|---:|
| `quota_manager_impl.cc` | 84 |
| `quota_manager_proxy.cc` | 30 |
| `quota_database.cc` | 13 |
| `usage_tracker.cc` | 10 |
| 나머지 6파일 | 16 |

동작은 바뀌지 않습니다(이미 fatal이었습니다). 바뀌는 것은 코드 생성으로, 인자가 없으면 공식 빌드에서 CHECK가 로그 문자열을 버립니다. 바이너리가 작아지는 대신 그 메시지가 크래시 리포트에 실리지 않는데, 이 트레이드오프를 CL 설명에 명시했습니다.

enum의 `M148 = 148,` 항목 자체는 이 CL에서 지우지 않았습니다. 트리에 아직 4곳(signin·media/audio/win·resource_coordinator)이 남아 있고, **그 항목을 지우는 CL은 `base/` 헤더를 건드려 전 트리 재빌드를 유발**하므로 비싼 쪽을 후속으로 미뤘습니다.

## 발굴 과정

만료된 `NotFatalUntil`을 훑는 것 자체는 앞선 기여에서 쓴 방법이었는데, 이번에는 **마일스톤 단위로 전 트리를 재집계**한 것이 결정적이었습니다.

```bash
git grep -oh "NotFatalUntil::M[0-9]*" -- '*.cc' '*.h' | sort | uniq -c   # 마일스톤별 분포
git grep -c "NotFatalUntil::M148" -- storage/browser/quota/               # 한 곳에 몰렸는지
```

그 결과 **M148은 사실상 quota 전용 마일스톤**임이 드러났습니다 — 트리 전체 157곳 중 153곳이 한 디렉토리에 있었습니다. 덕분에 OWNERS 한 그룹으로 끝나는 CL이 됩니다.

착수 근거로 가장 강했던 것은 **직전에 머지된 제 CL**이었습니다. [CL 8282239](https://crrev.com/c/8282239)에서 같은 디렉토리의 M148 마커 3개를 "as it is long past"라는 근거로 제거했고 그대로 승인·머지됐습니다. 같은 리뷰어가 같은 판단을 이미 한 셈이라, 별도로 의사를 타진할 필요가 없었습니다.

반대로 **가장 큰 덩어리인 M152(759곳, `content/browser/renderer_host`)는 착수하지 않았습니다.** 원 커밋이 `[dcheck-to-check] Convert DCHECKs ... [4/n]`이고 같은 저자의 열린 CL도 있어 **진행 중인 프로젝트의 일부**였기 때문입니다. 넣은 지 3개 마일스톤밖에 지나지 않았다는 점도 M148(7개 경과)과 달랐습니다.

## 테스트 방법

- `storage_unittests`의 quota 관련 테스트 **313/313 통과**
- 빌드는 증분으로 끝났습니다. `base/` 헤더를 건드리지 않는 CL이라 재컴파일 범위가 좁습니다 — 같은 시기에 `base/not_fatal_until.h`를 건드린 다른 CL이 13시간 풀빌드를 요구한 것과 대조적입니다.
- 편집이 정말 "인자 제거"뿐인지 기계적으로 검증했습니다. 각 파일의 원본에서 공백을 제거하고 `,base::NotFatalUntil::M148` 문자열을 지운 결과가 수정본과 정확히 일치하는지 비교해, 10파일 모두 일치함을 확인했습니다.

## 배운 점

- **정리 작업은 "몇 곳인가"가 아니라 "어느 경계에 몰려 있는가"로 범위를 정합니다.** 153곳이라도 한 OWNERS 그룹 안이면 리뷰어 한 명으로 끝나고, 30곳이라도 여덟 그룹에 흩어져 있으면 승인 수집이 병목입니다.
- **같은 종류의 만료 표식이라도 배경을 봐야 합니다.** M148은 팀의 일회성 작업이 7개 마일스톤 지난 잔여물이었고, M152는 지금도 진행 중인 프로젝트의 일부였습니다. 숫자만 보면 M152가 5배 크지만 손대면 안 되는 쪽입니다. `git log -L`로 그 줄이 언제 누구에 의해 왜 들어왔는지 확인하는 것이 판단의 핵심이었습니다.
- **자기 CL이 다음 CL의 근거가 됩니다.** 머지된 변경에 판단의 근거를 문장으로 남겨두면, 같은 판단을 다시 설득할 필요가 없어집니다.
- **큰 기계적 치환은 결과를 기계적으로 검증합니다.** 153곳을 눈으로 확인하는 것은 신뢰할 수 없어서, 정규화 후 문자열 비교로 "의도한 변경 외에 아무것도 바뀌지 않았음"을 증명했습니다.
